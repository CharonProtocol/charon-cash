The relayer is a Rust worker on Cloudflare's edge that holds the relayer keypair and the D1 mirror — and never a user key. Every read is answered from the mirror; the chain is touched only through one paid RPC; and indexing is lazy, a signature walk on demand instead of an always-on stream. Encoded constraints

What the code bakes in

The in-flight map is best-effort

A per-isolate Mutex with a 60 s TTL. Two isolates can race the same note. The durable backstops are the D1 spent-check and the on-chain nullifier constraint.

"submitted" is not "confirmed"

Path B returns right after sendTransaction. Only the admin ops poll (5 × 3 s). Clients confirm via /indexer/status or their own scan — the payroll flow polls /api/nullifier/:hash instead of trusting the response.

Reads degrade to stale

A failed sync on a read is warn-and-continue, so the mirror can lag. The forced pre-withdraw sync plus the 100-root history is what keeps freshly built proofs valid anyway.

Paid RPC is load-bearing

Public devnet RPC 403s Worker egress. SOLANA_RPC_URL must be Helius or equivalent — the whole worker is one fetch away from that secret.

Proofs come from the mirror

merkle.rs walks tree_levels as a full-layer path. Insertion-time shortcuts once produced stale proofs that failed ForceEqualIfEnabled on-chain — that is why step 5 of the validation chain checks the root against history, not against a recomputation.

Leaf order is execution order

The signature feed only guarantees slot granularity, so same-slot transactions are re-sorted by their position in the block (getBlock) before leaves are assigned — mirror indexes must match the program's append order exactly.
