The on-chain program · a deep dive

On-chain
program

A Pinocchio program — not Anchor — holding a height-26 Poseidon Merkle tree of commitments, an existential nullifier set, and a Groth16 verifier over BN254. Seven instructions; every private move is a 2-input / 2-output UTXO transaction.

Pinocchio Groth16 / BN254 Poseidon tree 7 instructions

The first byte of every instruction selects the handler. Transact (2) and TransactSpl (3) are the entire user path.

At a glance

Pinocchio. One byte dispatches seven paths.

Zero-copy #[repr(C)] Pod structs (bytemuck, no Anchor discriminators). The entrypoint splits the first byte off instruction_data and matches it to a handler — or rejects with InvalidInstructionData.

// programs/privacy-cash/src/lib.rs let (disc, data) = split_first(instruction_data)?; match PrivacyCashInstructions::try_from(disc)? { Initialize => process_initialize(data, ..), InitializeTreeAccountForSplToken => process_initialize_spl(data, ..), Transact => process_transact(data, ..), TransactSpl => process_transact_spl(data, ..), UpdateGlobalConfig => process_update_global_config(..), UpdateDepositLimit => update_deposit_limit(..), UpdateDepositLimitForSpl => update_deposit_limit_spl(..), }

declare_id!

Program ID 5Gcq…UJ9P is baked in at compile time. Account ownership is checked against crate::ID on every PDA.

No self-emit of compute budget

The program never sets its own CU limit. The client must prepend SetComputeUnitLimit — Groth16 verification is the dominant cost.

Validation is imperative

No #[derive(Accounts)]. Accounts are positionally destructured and checked by hand with verify_* helpers.

State on-chain

Four account types · five PDA seeds

Everything the program persists is one of four small Pod accounts, each a PDA.

GlobalConfig

One singleton. Holds authority and the fee schedule.

deposit_fee_rate=0 · withdrawal_fee_rate=25 bps · fee_error_margin=500 bps

MerkleTreeAccount

The tree: subtrees[26] frontier, root_history[100], next_index, max_deposit_amount.

One for SOL; one per SPL mint.

TreeTokenAccount

The SOL vault PDA — physically holds deposited lamports. Withdrawals/fees adjust it via set_lamports.

seed: "tree_token". SPL uses a real ATA instead.

NullifierAccount

A 1-byte account storing only bump. Existence = spent. Created fresh on each spend.

A constellation of rent-exempt PDAs, not a bitmap.

The core primitive

One instruction. Three behaviors.

Transact is a single 2-input / 2-output UTXO move. Nothing about the instruction name says “deposit” or “withdraw” — only the sign of ext_amount does.

ext_amount > 0 · deposit

The signer pays the vault. Two fresh output commitments are appended to the tree. You leave with an encrypted note.

ext_amount < 0 · withdraw

The vault pays a recipient + fee. Two input nullifiers are marked spent. The leaf you spend is never named.

ext_amount == 0 · transfer

A fully private swap or split inside the pool. No public value moves (only an optional fee). validate_fee is a no-op.

// state/transact.rs — the public signals of every proof pub struct Proof { a: [u8; 64], b: [u8; 128], c: [u8; 64], // BN254 points root, public_amount, ext_data_hash, // 32 each input_nullifiers: [[u8;32]; 2], output_commitments: [[u8;32]; 2], } pub struct ExtDataMinified { pub ext_amount: i64, // the sign is everything pub fee: u64, }
2 inputs (nullified) 2 outputs (committed) amounts · keys · blinding · path

Conservation is enforced in the field: public_amount = ext_amount − fee (deposit) or −(|ext_amount| + fee) (withdraw).

Security core

Five checks gate every Transact

All five run before a single lamport or token moves. Order matters — cheap state checks first, the pairing last.

01 · root in history

is_known_root(root) — the proof’s root must be one of the last 100 roots. Tolerates finality & reorgs.

else UnknownRoot (5)

02 · ext_data hash

Recompute SHA-256 over recipient, ext_amount, enc. outputs, fee, fee_recipient, mint — must equal the proof’s hash.

else ExtDataHashMismatch (6)

03 · public amount

Recompute public_amount from ext_amount & fee in BN254 Fr arithmetic; compare to the proof.

else InvalidPublicAmountData (7)

04 · fee bounds

fee ≥ |ext_amount| · rate · (1 − margin) against the configured deposit or withdrawal rate.

else InvalidFeeAmount (11)

05 · Groth16 verify

The pairing check over 7 public inputs: root, public_amount, ext_data_hash, 2 nullifiers, 2 commitments.

else InvalidProof (14)

Plus the double-spend guard (next slide): the two input nullifiers are init’d as PDAs before these gates even run — so a replay of the same proof can’t reach the pairing.

Transact · ext_amount > 0 · deposit SOL

Deposit — signer pays the vault

  1. Load & validate — verify_signer(signer), parse TransactArgs, check the tree / vault / config are initialized and their PDAs rederive.
  2. Cross-tree guard — verify_cross_nullifier(nullifier2, nullifier3): each must be empty or foreign-owned, blocking reuse on another tree.
  3. Mark the two input nullifiers spent — init_nullifier_account for nullifier0 & nullifier1 before any value moves. A replay hits AccountAlreadyInitialized.
  4. Root membership — is_known_root(root), else UnknownRoot.
  5. ext_data hash, public amount, fee bounds — recompute all three and compare to the proof.
  6. Groth16 verify — the pairing over the 7 public inputs, else InvalidProof.
  7. Deposit cap — ext_amount ≤ max_deposit_amount, else DepositLimitExceeded (1000 SOL default).
  8. Move SOL — CPI system::Transfer { signer → tree_token_account } for ext_amount.
  9. Append both leaves — MerkleTree::append for each output commitment; the new root enters the 100-root ring.

Transact · ext_amount < 0 · withdraw SOL

Withdraw — the vault pays out

Steps 1–6 are identical to the deposit (load → nullifier guard → nullifier init → root → hashes/amount/fee → proof). The branch diverges here:

  1. Solvency check — total = |ext_amount| + fee + rent_exempt_minimum; require vault.lamports ≥ total, else InsufficientFundsForWithdrawal (9).
  2. Pay the recipient — direct set_lamports: vault −= |ext_amount|, recipient += |ext_amount|. No CPI — the program owns the vault PDA, the runtime holds the sum invariant.
  3. Pay the fee (if fee > 0) — set_lamports vault −= fee, fee_recipient += fee.
  4. Append both output leaves — the change note(s) re-enter the tree; new root rotates into history.

The recipient and fee_recipient addresses come from the on-chain accounts passed in — not from the instruction data. They’re bound into the proof via the ext_data hash, so they can’t be swapped after the fact.

TransactSpl · the SPL path

Same proof, real token accounts

The five gates are identical. What changes is the tree keying and the value movement — it goes through SPL token accounts, signed by PDAs.

Per-mint tree

The tree PDA is ["merkle_tree", mint, bump] — every SPL token gets its own frontier, root history, and deposit cap.

16 accounts, validated by hand

Mint, the signer’s token account (checked owner == signer && mint == mint), recipient & fee-recipient ATAs, the tree_ata, token & ATA programs.

global_config owns the vault

The tree_ata’s authority is the global_config PDA. Every outflow is a TokenTransfer signed by that PDA.

Deposit — into the pool

CreateIdempotent the tree_ata (signer pays rent, no-op if it exists), then TokenTransfer signer_ata → tree_ata signed by the signer.

Withdraw — out of the pool

TokenTransfer tree_ata → recipient_token_account signed by global_config; the fee transfer is identical. No rent-exempt precheck — the token program rejects an over-spend.

Reentrancy-proof

Nullifier PDAs are init’d before any token transfer — the documented reason a callback can’t double-spend mid-flight.

Under the hood

Groth16 verifier & the Poseidon tree

Groth16 over BN254

The verifying key is a compile-time const, not an account. verify_proof deserializes A as a G1 point (on-curve check), negates it, endianness-swaps, then drives the alt_bn128 precompiles.

The pairing, concretely

prepare_inputs: 7× G1-scalar-mul + 7× G1-add. Then one alt_bn128_pairing_be over 4 pairs: (−A,B),(IC,γ),(C,δ),(α,β). Pass iff result is 1.

7 public inputs (in order)

root, public_amount, ext_data_hash, nullifier0, nullifier1, out_commit0, out_commit1. Everything else is private witness.

Incremental Poseidon tree

Height 26 → 226 leaves. Hashing is a 2-to-1 Poseidon via the sol_poseidon syscall (BN254, big-endian, Circom params). Commitments are inserted directly as leaves — no per-leaf hash.

Filled-subtree frontier

Only subtrees[26] is stored — not every leaf. Zero-hash siblings come from a precomputed constant. append() walks 26 levels and rotates the root.

100-root ring buffer

root_history[100] holds recent roots; is_known_root scans it once and rejects the all-zero root. No events — leaf index is read from next_index.

The binding

ext_data — how the proof is pinned to reality

The instruction carries only ExtDataMinified — the two fields not already in the account list. The program reassembles the full payload from the live accounts and hashes it.

// utils.rs — SHA-256, not Poseidon calculated = sha256( recipient // 32 — from the account || ext_amount.le(8) || u32.le(enc1.len) || enc1 || u32.le(enc2.len) || enc2 || fee.le(8) || fee_recipient // 32 — from the account || mint_address // SOL_ADDRESS for the SOL path ); // field-element compare (the subtle part) Fr::from_le_bytes(calculated) == Fr::from_be_bytes(proof.ext_data_hash)

Why it exists

Recipient, fee_recipient and mint cannot be circuit public inputs (too many). Instead they’re committed via this hash, which is a public input.

What it prevents

Swap the recipient, redirect the fee, change the amount, or switch mints — the recomputed hash no longer matches the proof, so the proof is void. A withdrawal can’t be redirected.

The endianness trap

Solana SHA-256 is little-endian; the circuit reads field elements big-endian. The prover must encode the digest big-endian, or the on-chain compare silently fails.

Double-spend defense

Nullifiers — existence is spending

A nullifier is spent if and only if its PDA account exists. The program never stores a value — it creates the account.

Same-tree: init before move

nullifier0 & nullifier1 are init’d via system::CreateAccount before any value moves. Spend the same proof twice and the second CreateAccount fails with AccountAlreadyInitialized.

Cross-tree: the swapped-prefix guard

nullifier2 / nullifier3 re-derive the same hashes under the other seed prefix. verify_cross_nullifier fails if either is program-owned & non-empty — closing the slot-swap loophole.

One-way by construction

The nullifier is a Poseidon digest of the note’s secret. Spending reveals it, but it can’t be inverted back to the leaf or your spending key — it’s the only on-chain link between a withdraw and a deposit.

Structurally reentrancy-proof

Because nullifier accounts exist before the token transfer begins, a malicious CPI mid-transfer cannot double-spend the same note — the second init is already doomed.

admin

Config & limits — then the guarantees

UpdateGlobalConfig

A bitmask (VALID_MASK = 7) selects which rate to write: deposit (1), withdrawal (2), margin (4). Each must be ≤ 10 000 bps, and verify_authority must pass.

UpdateDepositLimit(…ForSpl)

Sets max_deposit_amount on the SOL tree, or a per-mint tree (PDA re-derived with the mint). Authority-gated; no admin allowlist is compiled in today.

Gates before value

Root, ext_data hash, public amount, fee bounds and the pairing all pass before a lamport or token moves.

Double-spend impossible

Nullifier PDAs are created up front; a replay dies at CreateAccount, never at the pairing.

Funds can’t be redirected

Recipient & fee are on-chain accounts bound into the proof via the ext_data hash.

Vault stays solvent

SOL withdrawals must leave the rent-exempt floor; SPL over-spends fail inside the token program.

No trusted submitter

Whoever signs only pays gas & rent — the proof, not the signer, authorizes the move.
