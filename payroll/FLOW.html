Private Payroll — the whole flow

One employer, 16 pool wallets, 210 employees, 242 transactions, ~4 minutes — and nobody on-chain can prove which employee was paid from which deposit. This page walks the exact flow the engine runs, then explains the two ideas that make it fast: native proving and 16 parallel chains.

00The cast

employer

Treasury wallet

Holds the company SOL. Funds all 16 pools at the start. Its signature unlocks the private vault.

shielded

16 pool wallets

Intermediate shielded wallets. Each one owns a slice of the deposited funds as private notes and pays ~13 employees.

210

Employees

Receive normal SOL at their public address (v1) or a private note only they can spend (v2 shielded mode).

backend

Relayer + mirror

Builds each transaction's zero-knowledge proof from its D1 mirror of the note tree, signs nothing of yours, broadcasts.

chain

Solana + merkle tree

Every shielded tx appends 2 encrypted leaves to one tree and nullifies its input notes. This is the public ledger everything proves against.

01Four stages, top to bottom

Amounts shown for the benchmark run: salary 0.001 SOL (1,000,000 lamports) + relayer fee per pay.

stage 1
~14s

Deposit — public money enters the shielded pool

treasury ──deposit(0.2138 SOL)──▶ [leaf 0..1] encrypted notes owned by treasury

Public: the deposit amount and who sent it. Hidden: the note contents (amount, owner, blinding) — leaves are ciphertexts.

stage 2
~10s

Split — treasury shields funds to each pool

treasury notes ──transfer──▶ pool #k note (target for ~13 pays) + treasury change

One shielded transfer per pool (16 total). The input nullifier is spent, two new leaves appear. Public: nothing new — no addresses, no amounts. Hidden: which pool got how much.

stage 3
~200s

Payouts — 210 withdrawals, 16 at a time

pool #k note ──withdraw──▶ employee address gets 0.00101 SOL · pool change note (next pay's input)

Each pay consumes the pool's note and produces a change note — that change is the input of the next pay. This chain-of-change is why a pool pays serially. Public: recipient address + amount of each withdrawal. Hidden: which deposit funded it, the pool's remaining balance.

stage 4
anytime

Claim — employee side (v2 shielded mode)

employee wallet ──scan tree──▶ finds notes encrypted to them ──withdraw──▶ plain SOL

In shielded mode the payout itself is a private note; the employee's wallet scans the tree, decrypts what is theirs, and withdraws whenever they want. Public: nothing until they exit. Hidden: that they were paid at all, and how much.

02The mental model: 16 serial chains, run in parallel

The question this answers: "you said each transaction needs the previous one to land — so how is this parallel?" Both are true, at different levels.

pool 0
deposit→split→pay 1→pay 2→pay 3→…→pay 13
pool 1
deposit→split→pay 1→pay 2→…→pay 13
pool 2
deposit→split→pay 1→…→pay 13
…
pool 15
deposit→split→pay 1→…→pay 14

Inside one lane, everything is serial. Pay n+1 spends the change note created by pay n, and its proof is built from the mirror's view of the tree — so it must wait until pay n is indexed. One deposit → one split → ~13 pays, strictly one after another.

Across lanes, nothing waits for anything. Pool 7's chain never touches pool 2's notes. Every lane has its own deposit, its own split, its own chain of change notes. That is the entire trick: the 210 pays are not one queue of 210 — they are 16 queues of ~13, running at the same time.

Dependency rule in one line: a transaction depends only on the transaction that created the note it spends — the previous pay in its own lane. The engine funds all lanes up front (16 deposits) precisely so no lane ever has to look at another lane.

03Where the time went — and where it goes now

Same 210-employee run, localhost surfpool, three configurations.

JS prover (snarkjs)
902s
native prover, 2 waves of 8
271s
native prover, 16 lanes
230s

What changed: the zero-knowledge proof for each transaction moved from JavaScript (snarkjs, ~9.4s) to a compiled C++ prover (rapidsnark, ~1s) — same circuit, same keys, same output, just computed natively. Proving stopped being the bottleneck.

What's left: each pay's p50 is ~13s, and only ~1s of that is proving. The rest is waiting for the backend mirror to index the previous transaction — because the relayer builds every proof from mirror state, a pay can't even start until the mirror caught up. The mirror indexes at roughly 1 transaction/second, and 242 transactions at ~1/s ≈ 230s. That's the current floor, not the prover.

Path to 1 minute: (1) pay several employees per transaction — needs a v2 circuit with multiple payout legs; (2) prove against an older tree root (valid for the last 100 roots) so pays don't wait for indexing at all. Both are backend/engine work; the client side is already as parallel as it can get.

The privacy guarantee is linkability, not invisibility: entries and exits are public by design (that's what entering/exiting a shielded pool means), but the connection between them is hidden behind the merkle tree, nullifiers, and encrypted notes — the same construction Tornado-style pools use, plus per-note owner commitments.
