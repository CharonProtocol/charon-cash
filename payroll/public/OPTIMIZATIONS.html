private payroll — the optimization playbook

Nine changes between 902 seconds and 11.3

Every salary in this payroll is hidden inside a zero-knowledge proof: the chain checks the payment is honest without seeing who paid whom, how much, or to which address. Paying 210 people that way took 902 seconds on day one. Here is every optimization that brought it to 11.3 seconds — what was slow, what we changed, and what each change measurably bought. No guessed numbers: every figure comes from a logged run.

First, who builds the proofs? (read this before the list)

  • Day one (the slow design): the remote backend built every single proof itself, one after another. That was the bottleneck — not a feature.
  • Change #1 moved proving to the payer: the treasurer's own machine builds the proofs. The backend stopped being everyone's math department.
  • The "prover pool" (#4) also lives on the payer's machine — it's our own local Rust proving server. It is not the remote backend.
  • The relayer never builds proofs. It only signs & submits payout transactions and pays the gas. That's why a payroll run costs the treasurer at most one signature.

The nine optimizations

Each card: what was happening → why it was slow → what we changed → what it measured. Same machine, 16 payroll pools, 210 employees, every run.

#1

Move proving off the backend

902s → 271s
Before
The relayer backend kept a mirror of the merkle tree and built every salary's ZK proof itself — all 210, one after another, on one remote machine.
Problem
One centralized machine doing everyone's heavy math, serially. No tuning could fix a bottleneck that is architectural.
Change
Proof-building moved to the payer's machine. The backend keeps only its real job: relaying transactions.
Measured
Pay wall 902s → 271s. Same proofs, same chain — the work just moved to where it can run in parallel: the payer's CPU.
who does the work now → the treasurer's own machine
#2

Parallel proof lanes, capped

271s → 230s
Before
Proofs ran one after another on the payer's machine.
Problem
Unlimited parallelism thrashes RAM and CPU — everything slows down together.
Change
Run at most 4 proofs at once — a lane cap tuned to the machine.
Measured
271s → 230s with zero new hardware.
who does the work now → the treasurer's machine, 4-wide
#3

Local tree replica + native prover

230s → 126.4s
Before
Every proof needed fresh merkle-tree data from the backend — a network round trip per proof — and the prover was snarkjs: JavaScript, ~4 seconds per proof.
Change
Keep a local replica of the merkle tree (proofs build instantly, no round trips) and swap snarkjs for rapidsnark, a native C++ prover (~10× faster).
Measured
230s → 126.4s.
who does the work now → still the treasurer's machine, just faster
#4

Rust prover pool, in-process

126.4s → 81.3s
Before
Even rapidsnark was spawned as a fresh OS process for every proof — startup overhead each time.
Change
A persistent pool of 4 Rust (arkworks) prover processes, always warm, proving in-process. Note: this pool runs on the payer's own machine — it's our local prover server, not the remote backend.
Measured
Proof time 4.0s → 0.64s; pay wall 126.4s → 81.3s. Proving is now 98% of what's left — the bottleneck is finally honest.
who does the work now → a local Rust prover pool (payer's machine)
#5

batch3 circuit — 2 salaries per proof

81.3s → 30.9s
Before
One proof per salary. Proving was the wall, so the only way out was more work per proof.
Change
A new ZK circuit proving 2 salaries + change in one proof; new on-chain instruction TransactBatch3 with its own ceremony verifying key.
Measured
Proofs halved; payout txs 226 → 105; wall 81.3s → 30.9s.
pattern unlocked → more salaries per proof = proportionally faster payroll
#6

Slim the on-chain verifier

headroom (wall unchanged)
Before
Verifying a Groth16 proof on-chain burns compute units (CU) — the chain's CPU budget — and batch instructions were near the ceiling.
Change
Read the rent sysvar once per instruction instead of three times; reuse fixed stack buffers instead of allocating; replace a heavyweight math library with ~150 lines of purpose-built field arithmetic.
Measured
batch3 instruction at 184k–187k CU. This headroom is exactly what later lets #8 (batch5) exist.
who does the work now → the chain, more cheaply
#7

Bigger envelope — v1 transactions

30.9s → 17.7s
Before
Legacy Solana transactions cap at 1,232 bytes — one batch instruction fills the envelope, nothing else fits.
Change
Adopt the 4,096-byte v1 wire format: 3 batch instructions per tx (6 salaries). ALTs and compute-budget instructions dropped entirely — CU became a config field. Plus 2 CPU threads per prover.
Measured
Txs 105 → 48; fees, signing and network waits all ~3× lower; wall 30.9s → 21.2s → 17.7s.
who does the work now → fewer transactions, same proofs
#8

batch5 + the memo pad

17.7s → 12.7s · fee halved
Before
A wider circuit — 4 salaries per proof (batch5, own verifying key) — proves in the same 679ms… but the instruction needs 241,010 CU and a lone instruction only gets 200,000. Payouts die with "computational budget exceeded".
Discovery
Controlled probes exposed the chain's real rule: a transaction's budget is the sum of default per-instruction costs — the limit we request is ignored, and an unknown program defaults to 200k no matter what it actually costs.
Change
Pack a do-nothing SPL Memo as ballast: its default is a full 200k, its real cost ~0. [batch5, batch5, memo] = 600k budget, ~480k used → 8 salaries per transaction. Guards added for the 100-root history window (lane caps + auto re-prove past 90 slots).
Measured
32 txs, 210/210 paid, 0 failures, 0 re-proofs, wall 12.7s — and the fee halved to 6,250 lamports/salary, because 8 salaries share one transaction's fee.
the wall, packed around — not broken, routed
#9

append_many — stop hashing everything twice

CU −18.4% · 210/210 exact
Before
Each payment appends commitments to the merkle tree, and every append walks all 26 levels. Two commitments land side by side — so the second walk recomputed every level the first just built. Double work, every payment.
Change
Pair the two commitments under one shared level-0 hash: 26 hashes per pair instead of 52. Odd landings handled; unit-tested byte-equal against the shipped append.
Measured
239,715 → 195,497 CU per payment instruction (−18.4%, 18 chain samples). The wall clock doesn't move — proving is the limit — but every payment now fits a lone 200k budget.
Bonus
VARIED mode: 210 distinct salaries all land exact — every employee syncs and decrypts their own note, and the run fails unless all 210 hold exactly their own amount (210/210 exact, 12.56s). Unequal pay costs nothing. And run-210.sh boots the whole pipeline on any fresh machine: 11.32s.
same speed, fifth cheaper to run — and payroll-accurate to the lamport

One-line summary (for the podium)

"We attacked three things: where proofs are built (backend → the payer's machine), how fast they build (4s → 0.64s, in Rust, in a warm pool), and how much work fits in one proof and one transaction (1 → 4 salaries per proof, 8 per transaction). Result: a 15-minute payroll became 11 seconds — private, gasless, and accurate to the lamport."
