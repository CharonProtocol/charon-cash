Private payroll - measured journey

Paying 210 people in private, in 13 seconds

Every salary in this payroll is hidden inside a zero-knowledge proof: the chain checks the payment is honest without seeing who paid whom. The first version took 902 seconds to pay everyone. Proving and checking those proofs was too slow, so we rebuilt the pipeline piece by piece. This page lists every change, what it measured, and why it worked - ending at a wall we first hit, then beat.

The seven changes

Everything below was measured on the same machine (8 GB laptop, 4 proof workers), 16 payroll pools, 210 employees, 0.005 SOL each. No guessed numbers.

  1. Prove in Rust, not JavaScript

    The old prover was snarkjs (JavaScript): about 4 seconds per proof. A Rust prover (arkworks) proves the same circuit in-process, so no file hand-off, no process spawn.

    Measured
    proof time 4.0s → 0.64s per batch of 2 salaries
    Why
    same math, no JavaScript runtime and no disk round-trip per proof

  2. Pack 3 payments into one transaction

    Solana's classic transaction is capped at 1,232 bytes - one payment per transaction. The new v1 wire format allows 4,096 bytes, enough for 3 payment-instructions per transaction (105 transactions → 48).

    Measured
    pay wall 30.9s → 21.2s; 48 transactions, largest 3,206 B
    Why
    3× fewer transactions means 3× less fees, signing, and network waiting

  3. Keep proofs fresh (the root window)

    A proof must quote the tree's current root, and the chain remembers only the last 100 roots. Fast lanes overtake each other and old proofs get rejected (UnknownRoot). Two guards: limit how many groups run at once (8 slots), and re-prove automatically if the root ages past 90 slots.

    Measured
    0 lane failures, 0 re-proofs in the 210-run
    Why
    the guards match the true rate: 8 slots × 6 leaves = 48 fresh leaves < 100-root window

  4. Put the on-chain checker on a diet

    Checking a proof on-chain (Groth16 verify) burns compute units (CU) - the chain's CPU budget. We trimmed the verifier: fetch the rent value once per instruction instead of three times, reuse fixed memory buffers instead of building new arrays, and replace a heavy math library with 150 lines of purpose-built field arithmetic.

    Measured
    batch-3 payment instruction: 184k–187k CU on-chain (9 samples)
    Why
    every CU saved is headroom - steps 5 and 6 show why headroom decides everything

  5. The wider circuit - works, but the chain says no

    A new circuit proves 4 salaries at once (batch5, 10 public inputs). It proves in 0.68s - the same as the 2-salary circuit - and the instruction executes correctly on-chain: the proof verifies and 5 leaves land in the tree. But it needs 241,010 CU, and a lone instruction in a transaction gets only 200,000 CU. Payouts fail with computational budget exceeded.

    Measured
    batch5 proof 679ms p50; instruction 241,010 CU on-chain
    Why
    one instruction alone cannot hold 241k - but a whole transaction might; see step 6

  6. The memo pad - 8 salaries per transaction

    Controlled probes exposed the chain's real rule: the budget is the sum of default costs of the instructions inside the transaction, shared by them all - the limit we request in the config is ignored. An unknown program is budgeted at 200,000 CU default but can cost almost nothing to actually run. So each payout transaction now carries a do-nothing SPL Memo call as ballast: two batch5 payments plus the pad budget 600,000 and use about 480,000 - one transaction, 8 salaries, measured landing on-chain.

    Measured
    [b5, b5, memo] tx = 2,896 B, 8/8 paid in the smoke; then 210/210 paid in 12.7s, 0 failures
    Why
    the pad's default is big, its real cost is ~0 - it widens the pool without drinking from it

  7. The tree was hashing everything twice

    Every payment adds its commitments to the tree, and each addition walks all 26 levels of hashes. But two commitments land side by side - the second walk recomputes and overwrites every single level the first walk just did. So we now place the pair under one shared hash: 26 hashes for two commitments instead of 52. One guard: deposits drop single commitments too, so the code also handles landing on an odd slot. Only the finished root is recorded; half-built roots of a payment were never visible to anyone.

    Measured
    one payment instruction: 239,715 → 195,497 CU (18 samples, −18.4%) - every one now fits a lone 200,000 budget
    Why
    the wall clock does not move - proving is the limit - but every payment got a fifth cheaper to run

The wall, measured - then packed around

Probes on the test chain (surfpool 1.5.0 with the v1 feature) nailed the rule: a transaction's budget is the sum of default per-instruction costs - an unknown program counts as 200,000 CU, a System transfer as 3,000 - and the limit we request in the transaction config is ignored. The pool is shared sequentially: batch5 as the only instruction got 200k (died), batch5 plus a transfer got 203k (died), two batch5 plus a transfer got 403k - the first payment succeeded at 239,715 CU, the second starved.

The 12.7s run: 210/210 paid, 0 failures, 0 proof rebuilds, largest tx 2,919 of 4,096 bytes, on-chain tree exactly matched our local copy at 448 leaves - and the fee halved to 6,250 lamports per salary (50,000 per 8-salary transaction). The wall is pure proving again - 4 proof workers on an 8 GB laptop; more RAM would cut it further. Reruns with step 7 landed 11.7-14.2s - same wall, but every payment instruction now costs 195,497 CU instead of 239,715 (-18.4%, 18 chain samples).

What would unlock more than 8 salaries per transaction

1 - Three proofs per transaction (12 salaries): the budget arithmetic already works (3 × 239.7k + pad < 800k), but each transaction then appends 15 leaves - too many concurrent transactions would rotate the tree's 100-root history out from under in-flight payments. Needs a slower pipeline or a wider history window.

2 - A chain that honors the requested config limit - there the pad is unnecessary; one config field asks for the budget directly. On this chain, the memo pad does that job, measured.
