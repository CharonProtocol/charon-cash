How the system works

The whole flow, end to end - this is what the commits build.

  1. Upload, one signature. The treasurer's file is solved into exact deposits; the vault covers the run, so a second payroll needs zero wallet popups.
  2. The payer's machine proves every payout locally - an arkworks prover pool in Rust, in-process. Secrets never leave the device; the relayer only broadcasts.
  3. Payouts pack into 4,096-byte v1 transactions (3 standard transacts, or 2 batch5 transacts + memo pads) and a Cloudflare Worker relays them gaslessly.
  4. On-chain: append_many pairs the merkle appends, nullifiers burn spent notes, roots land in the 100-root history.
  5. Each salary lands as an x25519-encrypted note only its owner can decrypt (private mode), or as plain SOL at the address (public mode).
  6. Employees claim from their own app: sync notes, prove, withdraw - gasless, one signature.

Two tracks, one protocol

The same on-chain program answers both. Nothing about the app requires a custom circuit - the batch circuits are an optimization layered on top.

Standard circuit (what the app runs)Batch5 circuits (what the bench runs)
Pay wall, 210 salaries63.3 s (67.6 s unpacked)11.32 s
Payout txs80 (3 salaries/tx)32 (8 salaries/tx)
Salaries per proof14
Proofs required210 (+210 deposits)53 (+16 deposits)
Verifying keys1 - the protocol's own+2 (one ceremony per circuit)

Where the speed lives: the wall is roughly (number of proofs) x (per-proof time) / (provers). run-standard-v1.mjs pointed the batch pipeline's own machinery at the stock circuit - packing 226 txs down to 80 moved the wall only 67.6 → 63.3 s (~6%). The batch circuits buy the other ~5.6x by proving 4 salaries per proof: 53 proofs instead of 210. That is the whole difference - it lives in the circuit, nowhere else. Both tracks end the same way: 210/210 paid, 0 failures, on-chain tree equal to the local replica.
