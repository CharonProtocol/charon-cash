The 1,232-byte wall

Batch payout tx — largest of 112, at pay 5,000,000
1,216 B used1,232 B Solana packet limit
Why 2 employees per proof and not more. Solana’s 1,232-byte transaction packet is the binding constraint, not the prover. Each extra employee adds a ~121-byte encrypted note; a proof paying 4 employees exists and proves offline (736 ms/proof, measured earlier), but its transaction cannot fit in any Solana packet. 2-per-proof with a shared lookup table lands at 1,216 B with 16 B to spare. Getting past this needs a different encoding or client-built proofs — not a bigger circuit.
Bigger pays break the old path first. Measured today: a 1-to-1 payout at 50,000,000 lamports serializes to 1,233 bytes — one byte over — and is rejected, because the SDK’s single-payout path carries no lookup table. The batch path is the one with headroom.

Answers

  • Is batching really faster end-to-end? Yes — 2.55× on the pay phase, 1.55× end-to-end after paying its own 20 s setup, with zero failures on either side.
  • What does it cost? Nothing per employee: identical 12,500-lamport fee, same Groth16 verification on-chain, 1.875× fewer signatures and transactions for the chain to carry.
  • What’s the ceiling? 2 employees per proof — the packet limit, not the prover. Sub-minute for 210 needs client-built proofs or a leaner output encoding.
  • Is the old path untouched? Yes. Transact (1-to-1) is byte-identical to before; TransactBatch3 ships beside it as instruction 7 with its own verifying key. Both ran clean in the same session.
  • Context for the 84 s baseline. That number is itself 2.7× faster than the best 230 s of the relayer-built-proofs era — in-process arkworks provers plus client-signed transactions did that; batching stacks on top of it.

Conditions & verification

  • Chain wiped, program re-deployed, D1 re-migrated, mirror re-synced before each side (bench/reset-env.sh); both sides started from leaf 0, genesis root.
  • Same 16 employer pools, same 210 registered recipients (13–14 per pool), same pay of 5,000,000 lamports, same four parallel provers, same relayer and proxy.
  • After each run the on-chain tree PDA was read back and compared to the mirror: next index and root matched exactly (452/452 and 368/368 leaves), final root present in root history.
  • Fresh local ceremony for the batch circuit (powersoftau pot15 → Groth16), verifying key embedded in the program, swap convention diffed byte-for-byte against the production circuit’s key.
  • Employee outputs are standard encrypted notes, same format as 1-to-1 payouts, so the existing withdrawal flow is unchanged (withdrawals were not exercised in this bench).
