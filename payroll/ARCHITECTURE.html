The three planes

Everything private lives client-side. The relayer never sees secrets — it mirrors the chain so clients can build proofs, and broadcasts signed transactions. The program holds only commitments, nullifiers, and a root history. Follow the numbered loop.

client

Wallet SDK

Owns the spending key. Notes are poseidon(amount, pubkey, blinding) leaves; proofs take ~4 s of CPU each. The wallet signs; nothing secret ever leaves this plane.

backend

Relayer on Workers

D1 mirrors every leaf and tree level so clients get Merkle paths without scanning the chain. A lazy indexer walks program signatures on demand, in block order, and the relayer broadcasts pre-signed transactions gasless-style.

on-chain

Privacy-cash program

Verifies the Groth16 proof, checks the public root against a 100-entry history, inserts two output commitments, writes nullifiers, and moves SOL through a PDA vault. A transact costs ~209k CU.

invariant

One mirror, one chain

Every fix below exists to keep one statement true: the root a client proves against is a root the program still remembers. When they drift, every transaction dies with UnknownRoot (0x5).

Anatomy of one private payment

A transfer spends one note and mints two: the recipient’s output and the treasurer’s change. The change funds the next payment — that chain is what payroll runs down. The sequence plays when it scrolls into view.

  • Prove. The witness asserts the input path hashes to the public root — inCheckRoot <== inTree.root — so a stale path or root fails client-side before any SOL moves.
  • Send. The wallet signs; the relayer broadcasts. Fee floors at 10,000 lamports when basis points would compute lower.
  • Land. The program accepts the root only from its last 100 roots — proofs age out after 100 newer transactions anywhere in the pool.
  • Re-index. The indexer appends the tx’s two commitments to the mirror. Same-slot transactions are ordered by their position in the block, because that is the order the program assigned leaves in.
  • Recover the change. The client decrypts a window of fresh leaves and matches on blinding factor to find its own change note — never on amount, which is not unique across parallel workers.

The race log

Seven ways the system silently broke under concurrency. Each entry: the exact symptom we saw, the cause, and the fix that shipped.

Root and path fetched in two calls

fixed · 43ab0b8 + bc87ef0
symptom
Witness calculator throws ForceEqualIfEnabled_288 / Transaction_291 — the path does not hash to the claimed root.
cause
Root came from /api/merkle/sol, paths from /proof/:leaf. Between the two calls another worker’s tx landed and the tree advanced — proof built against a root that no longer matched its own paths.
fix
The proof endpoint now returns root and next_leaf_index inside the same response; the SDK re-fetches all input proofs until every one agrees on a single root before proving.

Deposit notes stored at a guessed leaf

fixed · bc87ef0
symptom
Transfers spending a just-deposited note fail witness checks — the note sits at the wrong leaf index.
cause
The SDK stored the deposit note at the pre-send nextLeafIndex guess. With transactions landing in parallel, the true position shifted by the time the deposit confirmed.
fix
After landing, decrypt a window of leaves around the guess and match on the note’s blinding factor; the store is corrected to the true index before the note is ever spent.

Same-slot transactions indexed out of order

fixed · 67a54c5
symptom
Every transaction starts failing on-chain with custom program error: 0x5 (UnknownRoot) after a parallel fan-out — including fresh deposits on an idle tree.
cause
getSignaturesForAddress orders same-slot transactions by feed position, not execution order. Two txs landing in one slot were indexed with their leaf pairs swapped: right commitments, wrong indexes. The mirror’s root diverged from the program’s root — 90 of 100 history roots matched, then nothing did.
fix
The indexer sorts pending signatures by slot and, within a slot, by position in that block (getBlock) — exactly the order the program assigned leaf indexes in. Mirror wiped and rebuilt from genesis: 794 txs, 100/100 roots matching.

Change notes recovered by leaf-index guess

fixed · e5d67f0
symptom
A worker adopts the wrong change note mid-chain — change amount 12120000 != expected 11110000 — then every later payment in that chain fails.
cause
The chain anchored the next note at leafIndex + 1 from its own receipt. With 16 workers landing simultaneously, other pools’ outputs interleave and the anchor points at someone else’s note. Amounts can’t disambiguate: parallel pools hold identical values.
fix
WithdrawResult now returns the fresh change note’s blinding factor. After refreshNotes, the worker finds its change by blinding match — the one value unique to this tx — and the chain continues from the true note.

Fees below the relayer floor

fixed · 39713ab · bcd6393 · fd21dd4
symptom
Small transfers die in BigInt sinks or get rejected: the contract’s minimum fee (10,000 lamports) beats the basis-points computation on 1M-lamport sends.
cause
25 bps of a small transfer is far below the on-chain minimum; the client and relayer disagreed on which number wins.
fix
The floor wins everywhere, by construction: SDK floors its estimate, the payroll engine validates before constructing amounts, and the relayer rejects anything under the minimum before it reaches the chain.

Sixteen workers converge on one note

fixed · payroll branch
symptom
Under 16-way contention almost every first attempt fails with a withdrawal … is already being processed, the retry wave dies with already been spent, and a 32-pay reproduction nets 5/32 paid even though transactions keep landing on-chain.
cause
All 16 pay chains spend notes owned by the same treasurer key. The entry syncNotes rebuilds each worker’s note set from the indexer — so every worker ends up holding all 16 pool notes — and selection spends the largest note. Sixteen workers converge on the same input; the first one through the relayer’s in-flight guard wins, the other fifteen fail, and their retries converge on the next shared note.
fix
transferNoteSOL/SPL accept inputNote { blinding }: selection is filtered to the named note, with a loud error if it is missing or too small. Each pay chain pins its own active change note, so concurrent chains can never converge.

A landed tx misread as failed

fixed · payroll branch
symptom
A pay tx lands on-chain but its caller only sees an error; the retry rebuilds a spend of the same nullifiers and dies with already been spent.
cause
The relayer holds each relay request through a confirmation window while concurrent traffic queues behind its guard. When the response dies at the transport layer the caller holds no receipt — and no identity for the change note it just minted. The relayer’s in-flight set also leaked: entries were only removed on submit errors, never on success, so a lost request could block its own retry forever.
fix
Three layers. The SDK’s onSubmitted journals { nullifiers, changeBlinding, changeAmount } right before the relay POST, so the pending change identity survives the transport. The relayer bounds its in-flight guard with a 60s TTL, shortens the confirm window to 15s, and names the landing tx in spent-nullifier errors. The payroll worker recovers by probing for the journaled blinding and continues the chain from the true change note.

The payroll fan-out

Paying 210 people as 210 independent deposits is both slow and loud — 420 transactions and a public deposit per paycheck. The split-tree does it with one visible deposit and 227 transactions: deposit once, split into 16 pool notes, then run 16 pay chains in parallel.

Each chain is a worker process holding exactly one active note: pay the recipient, find the change note by decrypting fresh leaves and matching blinding, pay again. Workers share the treasurer key, so note ownership is decided by blinding match — amounts are identical across pools and would be ambiguous.
