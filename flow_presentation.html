Slide 01 · Pinocchio Program

Pinocchio Program Architecture

Privacy Cash runs on a zero-dependency Pinocchio C/Rust Solana program with 1-byte instruction tags, client-side WASM proofs, direct RPC deposit submission, and optional gasless relayer withdrawals.

⚡ 1. Pinocchio Program

Custom 0-dependency Solana program using pinocchio::{entrypoint, AccountView} for maximum throughput and zero overhead.

📡 2. Direct RPC Dispatch

Deposits & Direct Withdrawals bypass the relayer! Wallet signs raw transaction bytes directly to Solana RPC node.

🔒 3. Client ZK Prover

Browser computes Poseidon hashes & Groth16 witness locally in WebAssembly. Zero private keys touch the server.

⚡ 4. Relayer / Indexer

Indexer logs RPC event logs to SQLite cache. Relayer acts as fee-payer only for 0-SOL recipient withdrawals.

Slide 02 · Step 1

1. Client Offline Note Construction

When the user initiates a deposit, the client SDK creates a 256-bit secret commitment completely offline inside browser memory.

Cryptographic Mechanics

1. WebCrypto CSPRNG generates 32-byte secret & 32-byte nullifier.

2. Light Hasher / Poseidon computes commitment: C = Hash(nullifier, secret).

3. Note data is encrypted using AES-GCM 256-bit derived from wallet signature.

4. Encrypted note string is stored in user's browser LocalStorage/IndexedDB.

// Client SDK: Note Construction (crypto.ts)
const secret = crypto.getRandomValues(new Uint8Array(32));
const nullifier = crypto.getRandomValues(new Uint8Array(32));

// Poseidon Hasher over BN254 Field
const commitment = poseidon([
  bytesToBigInt(nullifier), 
  bytesToBigInt(secret)
]);

console.log("Leaf Commitment Hash:", commitment.toString(16));
Slide 03 · Step 2

2. Direct RPC Submission & Pinocchio Deposit

No backend relayer for deposits! The depositor wallet signs the transaction and sends raw bytes directly to Solana RPC node.

PINOCCHIO DEPOSIT PIPELINE
1
Client SDK constructs VersionedTransaction with Pinocchio Transact = 2 / TransactSpl = 3 tag.
2
User Wallet signs transaction: signer.signTransaction(tx).
3
Direct RPC Dispatch: conn.sendRawTransaction(signed.serialize()). Bypasses relayer!
4
Pinocchio Program escrows SOL in Vault PDA & inserts commitment leaf into 20-level Merkle Tree.
// Client SDK (client.ts)
const signedTx = await this.signer.signTransaction(tx);

// DIRECT SOLANA RPC SUBMISSION (Bypasses Relayer!)
const txId = await this.conn.sendRawTransaction(
  signedTx.serialize(), 
  { skipPreflight: false, maxRetries: 5 }
);

await this.conn.confirmTransaction(txId, "confirmed");
Slide 04 · Step 3

3. Indexer Asynchronous Event Indexing

The backend Indexer runs asynchronously. It monitors Solana RPC logs to cache Merkle tree leaves and spent nullifiers in SQLite.

1. WebSocket RPC Logs

Indexer subscribes to Pinocchio log events: DepositEvent { leaf_index, commitment }.

2. Merkle Tree Cache

Updates local SQLite tree database so clients can quickly fetch Merkle inclusion paths via /api/merkle/proof.

3. Client Sync Poll

Client SDK calls waitForLeaves() or syncNotes() to confirm leaf index assignment.

Slide 05 · Step 4

4. Off-Chain ZK Proof Synthesis (snarkjs WASM)

To withdraw, the browser fetches the Merkle path from Indexer and computes a Groth16 witness locally in ~350ms.

Zero-Knowledge Security

• Proves ownership of a leaf in the Merkle Tree without revealing leaf index.

• Proves nullifier_hash = Hash(nullifier) matches note secret.

• Binds proof to recipient address & extDataHash.

• Private inputs (secret, blinding, Merkle path) **never leave browser memory**.

// Browser snarkjs Groth16 Witness Calculation
const { proof, publicSignals } = await snarkjs.groth16.fullProve(

    root: merkleRoot,
    publicAmount: publicAmount,
    extDataHash: extDataHash,
    inputNullifier: [nullifier0, nullifier1],
    outputCommitment: [commit0, commit1],
    inPrivateKey: [secret0, secret1],
    inPathElements: path.elements,
    inPathIndices: path.indices,
  },
  "/wasm/withdraw.wasm",
  "/zkey/withdraw_final.zkey"
);
Slide 06 · Step 5

5. Withdrawal Branching: Direct RPC vs Relayed

Withdrawals support two execution paths depending on recipient account status.

PATH A: Direct RPC Withdrawal

Used when wallet has SOL gas balance:

1. Client generates ZK proof in browser.

2. Client builds transact transaction.

3. Depositor wallet signs transaction.

4. Sent DIRECTLY to Solana RPC (`sendRawTransaction`).

PATH B: Gasless Relayed Withdrawal

Used for 0-SOL fresh target recipient address:

1. Client generates ZK proof in browser.

2. Sends proof payload to Relayer: POST /api/relay/withdraw.

3. Relayer checks fee rates & pre-verifies proof off-chain.

4. Relayer signs as gas fee-payer & submits to Solana RPC.

Slide 07 · Step 6

6. Pinocchio Program On-Chain Verification

The Pinocchio program evaluates elliptic curve pairing checks and records Nullifier PDAs to prevent double spending.

Pinocchio Program Execution (lib.rs)

1. Entrypoint parses 1-byte tag: PrivacyCashInstructions::Transact = 2.

2. verify_groth16() checks BN254 curve pairing equation against verification key.

3. Asserts Nullifier PDA: seeds = [b"nullifier0", nullifier_hash] does not exist.

4. Creates Nullifier PDA marker account to lock note against double-spending.

5. Transfers funds from Vault PDA escrow to clean recipient address!

// Pinocchio Program Entrypoint (lib.rs)
entrypoint!(process_instructions);

fn process_instructions(
    _program_id: &Address,
    accounts: &[AccountView],
    instruction_data: &[u8],
) -> ProgramResult {
    let (discriminator, data) = instruction_data.split_first()?;
    match PrivacyCashInstructions::try_from(discriminator)? {
        PrivacyCashInstructions::Transact => process_transact(accounts, data)?,
        PrivacyCashInstructions::TransactSpl => process_transact_spl(accounts, data)?,
        _ => Err(ProgramError::InvalidInstructionData),
    }
}

Slide 09 · Technical Specs

Pinocchio Discriminators & Wire Formats

Technical breakdown of Pinocchio 1-byte instruction tags and ALT address optimization.

Pinocchio Discriminator Enum

• 0: Initialize — Initialize SOL Merkle Tree PDA.

• 1: InitializeTreeAccountForSplToken — Initialize SPL Tree PDA.

• 2: Transact — Native SOL deposit & withdrawal.

• 3: TransactSpl — SPL Token (USDC/USDT) deposit & withdrawal.

• 4: UpdateGlobalConfig — Update fee rates (bps).

• Address Lookup Tables (ALT): Compresses account array to stay within 1232-byte MTU limit.

// Pinocchio Instruction Enums (constants.ts)
pub enum PrivacyCashInstructions {
    Initialize = 0,
    InitializeTreeAccountForSplToken = 1,
    Transact = 2,
    TransactSpl = 3,
    UpdateGlobalConfig = 4,
    UpdateDepositLimit = 5,
    UpdateDepositLimitForSpl = 6,
}
