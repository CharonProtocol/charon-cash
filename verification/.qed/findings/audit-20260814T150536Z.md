## 1. CRITICAL — `tree_ata` never bound to `mint` outside the deposit branch (SPL vault drain)

- **Location:** `src/instructions/transact_spl.rs:106-212` (`process_transact_spl`)
- **Evidence state:** **confirmed** — reproducer fired against the compiled program and drained the real vault; fix applied and reproducer re-run to confirm rejection
- **Severity:** CRITICAL
- **Status: FIXED.** `src/instructions/transact_spl.rs` now checks `tree_ata`'s recorded SPL mint against `mint.address()` whenever `tree_ata` already exists (i.e. on every path except a first-ever deposit, which is instead validated by the existing `CreateIdempotent` call). See "Reproducer and fix" below.

### The bug

`tree_ata` (the token vault the instruction moves funds into/out of) is address-checked against `mint` in exactly one place: the `CreateIdempotent` call inside the `ext_amount > 0` (deposit) branch, which the associated-token-account program internally validates against `(wallet=global_config, mint, token_program)`. On the withdrawal branch (`ext_amount < 0`, lines 190-197) and the fee branch (`fee > 0`, lines 200-208), `tree_ata` is passed straight into `pinocchio_token::instructions::Transfer` with **no address or mint check against the `mint` account used everywhere else in the instruction** (`ALLOWED_TOKENS` check, `tree_account` PDA derivation at line 115-119, `ext_data_hash` binding).

`pinocchio_token::instructions::Transfer` (confirmed by reading `pinocchio-token-0.5.0/src/instructions/transfer.rs`) is the legacy SPL `Transfer` (discriminator 3) — it carries no mint field. The real SPL Token program's own `Transfer` processor only requires `from.mint == to.mint`; it does **not** check either against a third `mint` account, because there isn't one in this instruction. So the only thing stopping `tree_ata` from being an arbitrary vault is the authority check, and `global_config` is the **shared** SPL-vault PDA authority for every mint's tree ATA (per `CLAUDE.md`: "GlobalConfig ... also doubles as the SPL vault's PDA authority"). Every tree ATA under this program has `owner = global_config`, regardless of mint.

### Exploit sketch

Config confirmed exploitable as deployed (`src/constants.rs:7,12`): `ADMIN_PUBKEY = None` (permissionless), `ALLOW_ALL_SPL_TOKENS = true` — so `InitializeTreeAccountForSplToken` lets anyone stand up a tree for a mint they created and control the mint authority of.

1. Attacker creates `MINT_B`, mints themselves an arbitrary supply, calls `InitializeTreeAccountForSplToken` for `MINT_B` (unrestricted — no admin gate, no allowlist gate).
2. Attacker deposits into `MINT_B`'s own tree via the legitimate deposit path (real `CreateIdempotent`-checked `tree_ata` = `MINT_B`'s real vault), building up a provable positive balance in that tree — `MINT_B` costs them nothing to mint.
3. Attacker generates a valid withdrawal proof against `MINT_B`'s tree/nullifiers (all internally consistent: `mint` account = `MINT_B`, `ext_data_hash` binds `MINT_B`'s address, `check_public_amount`/ZK proof validate against `MINT_B`'s own commitments — this is all attacker-controlled and self-consistent).
4. In the withdrawal transaction, attacker substitutes **`tree_ata` = the real vault ATA of a different, valuable mint `MINT_A`**, and `recipient_token_account` = an account they own with mint `MINT_A` (so the SPL Token program's `from.mint == to.mint` check passes trivially — both are `MINT_A`).
5. `tree_account` (state PDA) and `mint` still correctly resolve to `MINT_B`, so `verify_pda` at line 115-119 passes; the ZK proof, nullifiers, and `ext_data_hash` all check out against `MINT_B`. Nothing in the function ever asserts `tree_ata`'s mint equals `mint`.
6. `TokenTransfer { from: tree_ata (MINT_A vault), to: recipient_token_account (attacker's MINT_A account), authority: global_config }.invoke_signed(...)` succeeds — `global_config` is a valid signer for **any** tree ATA — draining real `MINT_A` funds using a proof that only cost the attacker a free self-mint.

Existing test coverage does not catch this: `spl_transaction_fails_for_modified_mint` (`tests/spl_tests.rs:5245`) only varies the `mint` account on the **deposit** path while keeping `signer_token_account`'s real mint fixed, which trips the *unrelated* `signer_token.mint() != mint.address()` check at `transact_spl.rs:65`. It never exercises a withdrawal with a `tree_ata`/`mint` mismatch.

### Fix applied

`src/instructions/transact_spl.rs`, right after the existing `signer_token` mint check:

```rust
// Bind `tree_ata` to `mint`. On a first-ever deposit `tree_ata` doesn't
// exist yet and is validated instead by `CreateIdempotent` below; on
// every other path (withdrawal, fee payment, or a repeat deposit) it
// already exists and must belong to this tree's mint, or `global_config`
// -- the shared SPL-vault authority for every mint's tree -- could be
// used to sign a transfer out of a completely different mint's vault.
if !tree_ata.is_data_empty() {
    let tree_ata_account = TokenAccount::from_account_view(tree_ata)?;
    if tree_ata_account.mint() != mint.address() {
        return Err(PrivacyCashError::InvalidMintAddress.into());
    }
}
```

Gated on `!tree_ata.is_data_empty()` rather than applied unconditionally, because a first-ever deposit's `tree_ata` legitimately doesn't exist yet at this point in the function (it's created a few lines later by `CreateIdempotent`, which performs its own address-derivation check). Every other case — withdrawal, fee-only, or a repeat deposit — requires `tree_ata` to already exist, so the check is live exactly where the vulnerability was.

### Reproducer and fix — verified

Added `security_finding_cross_mint_tree_ata_drain` to `tests/spl_tests.rs`. It:
1. Funds `ctx.spl_tree_token_account` (the real, single victim vault `setup()` already provisions) directly via `MintTo`, standing in for prior honest deposits.
2. Has the attacker create their own mint (mint authority = attacker, so supply is free), initialize a tree for it (permissionless), and deposit into it via one real Groth16 proof (`ark-circom`/wasmer, matching the rest of this suite).
3. Builds a second real withdrawal proof valid only against the attacker's own tree/nullifiers, then submits `TransactSpl` with `spl_tree_ata` swapped to the real victim vault and `recipient_ata` swapped to the attacker's real-mint ATA — everything else (`tree_account`, `mint`, nullifiers, proof) still the attacker's own.

**Pre-fix:** `cargo test --test spl_tests security_finding_cross_mint_tree_ata_drain -- --nocapture` — transaction succeeded, drained exactly `withdraw_amount` (900,000 raw units) from the real vault into the attacker's real-mint account, leaving the attacker's own (worthless-mint) vault untouched — confirming the drain came from the wrong tree entirely. Log: `CRITICAL (confirmed): cross-mint tree_ata substitution drained 900000 raw units from the real victim vault using a proof valid only against a free, attacker-controlled mint's tree.`

**Post-fix:** same test (now asserting rejection instead) — transaction fails with `InvalidMintAddress`; both the victim vault and attacker's real-mint account are byte-for-byte unchanged. `cargo build-sbf` clean.

**Regression run (full, post-fix):**
- `cargo test --test sol_tests` (isolated, `--test-threads=1`): **30/30 pass**, 133s.
- `cargo test --test spl_tests` (isolated, `--test-threads=1`): **21/21 pass**, including `security_finding_cross_mint_tree_ata_drain`, 91s.
- `cargo test --test spl_mint_tests`: 1 pre-existing failure (`fails_deposit_instruction_for_non_usdc_token_mint`), confirmed via `git stash` to fail identically on the pre-fix code — unrelated to this fix (it drives `TransactSpl` with the *native SOL* tree PDA as `spl_tree_account` on purpose, expecting an early reject; that reject now fires from a different, earlier check under the current `ALLOW_ALL_SPL_TOKENS = true` config than the test's `InvalidMintAddress` expectation, a pre-existing test/config drift). Not touched by this change.
- `cargo test` (all four binaries concurrently, the default): hung ~40 min on `sol_tests` (futex wait, near-zero CPU) and was killed. Not reproducible running `sol_tests` in isolation (30/30 pass in 133s) — looks like resource contention between concurrently-running wasmer/proof-generation thread pools across test binaries, not a functional regression. Recommend running this suite's binaries sequentially (`--test-threads=1` per binary, one binary at a time) rather than via a bare `cargo test`, independent of this fix.
- `bench` (compute-unit benchmarks) not run — not correctness-relevant to this finding.

**Conclusion: the vulnerability is fixed and verified**, with no regressions in the functional test suites.

### Suggested `.qedspec` regression guard

A `state`/`effect` clause asserting `tree_ata.mint == mint.address()` (or equivalently, that `tree_ata`'s address equals the derived ATA for `(global_config, mint)`) as a structural precondition of `TransactSpl`, so codegen emits a Kani/proptest harness that fails without the fix.

Also reviewed in the follow-up pass:

- `src/instructions/initialize.rs` (native SOL singleton init): structurally identical gating to the SPL tree init already reviewed — permissionless (`ADMIN_PUBKEY = None`) first-caller-wins on a fixed, mint-independent PDA seed. `verify_uninitialized` blocks re-init. The only residual risk is a deploy-time front-run of who becomes `authority`, which is an operational/deployment concern inherent to a permissionless singleton init, not a code defect, and already implied by the current `ADMIN_PUBKEY = None` configuration. No finding.

Treated as a trusted primitive per the framework-trust boundary in `VERIFICATION_SCOPE.md`-style scoping; the pairing arithmetic itself was not independently re-derived (matches the CLAUDE.md-documented trust boundary: "Trust (axioms): ...
