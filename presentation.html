The problem

Solana is public.
Spending shouldn’t be.

Every transaction is visible to everyone, forever. Privacy Cash lets you deposit SOL or SPL tokens, hold a secret “note,” and later withdraw to a brand-new address. A zero-knowledge proof proves you own the funds without revealing which deposit they came from.

01 · Deposit

Drop funds into the pool. You receive an encrypted note only you can read — the proof of ownership.

02 · Mix

Funds sit in a shared pool backed by a Merkle tree of commitments. There is no link on-chain to you.

03 · Withdraw

Prove you own a note and withdraw to a fresh address. Your wallet signs and sends it straight to the RPC — no relayer in the path.

Not fixed denominations — a 2-input / 2-output UTXO model, so amounts are flexible and can be split or joined.

main

The on-chain program

Built with Pinocchio (not Anchor). It holds a height-26 Poseidon Merkle tree of commitments, a nullifier set, and a Groth16 verifier over BN254. Each transaction is a 2-input / 2-output UTXO move.

The zero-knowledge proof

What it proves — and what it hides

The circuit (transaction2, 2-in/2-out, depth 26) proves: “I know a leaf in the tree, its nullifier secret, and a valid path to the root” — without revealing which leaf.

Public — visible on-chain

merkle root public amount ext-data hash 2 nullifiers 2 output commitments
What the chain checks against the verifying key.

Private — never leaves your machine

spending key blinding amount merkle path
The witness. The chain never sees it.

The nullifier is a one-way function of your key — the only thing that links a withdraw to a deposit, and it can’t be inverted to find you.

Deposit · pcash deposit

Deposit goes straight to the chain

Your wallet signs and sends it straight to the RPC — no relayer in the path.

  1. Generate a shielded key and secret note — a random blinding factor, full field entropy.
  2. Compute the commitment — Poseidon(amount, pubkey, blinding, mint).
  3. Build a Groth16 proof with ext_amount > 0 (this is a deposit).
  4. Build & sign the Transact instruction, send it directly to the program — your wallet pays the gas.
  5. The program verifies the proof, appends the commitment as a new leaf, and initializes the nullifier.
  6. The indexer records the new leaf and nullifier in Postgres.

Withdraw · pcash withdraw — the centerpiece

Withdraw goes straight to the chain too

  1. Fetch the Merkle path for your note from the backend’s read-only API — /api/merkle/…/proof.
  2. Build a Groth16 withdrawal proof (ext_amount < 0), bound to the recipient and fee.
  3. Build the Transact / TransactSpl instruction — prepends idempotent ATA creation for recipient & fee recipient, pool pays funds & fee.
  4. Your wallet signs the versioned tx and the SDK submits it direct to the RPC.
  5. The program verifies the proof, checks the nullifier isn’t spent, and pays the recipient.

feat/backend

Indexer — the chain, mirrored

Its job: turn the chain into a queryable database so clients can build proofs.

How it watches

A Yellowstone gRPC stream subscribes to every confirmed, non-failed program transaction. It decodes each Transact / TransactSpl to extract commitments, nullifiers, and encrypted outputs.

What it stores — Postgres

Leaves (commitments + encrypted outputs), the nullifier set, and the tree cursor. The Merkle tree itself is rebuilt in memory on demand.

What it serves

Over HTTP: all leaves, all nullifiers, the current Merkle root, and a Merkle proof for any leaf index.

Privacy model

Clients download everything and scan locally. The indexer never learns which notes are yours — there is no “notes owned by X” endpoint by design.

feat/backend

Backend — read-only chain mirror

No relayer. The backend only indexes the program and serves data — it never signs or submits a transaction.

  1. Yellowstone gRPC streams every Transact from the program.
  2. Decode the proof, ext-data, nullifiers and output commitments.
  3. Mirror the Poseidon Merkle tree; write leaves + nullifiers to Postgres.
  4. Serve read-only: /api/merkle/…/proof, root, nullifier status, fees.

What it does not do

It holds no signing key for your funds, never pays gas, and can’t redirect a withdrawal — the recipient is baked into the proof your wallet signs. The submit path lives entirely in the client SDK.

Why we still run it

Merkle proofs, known roots and nullifier status are shared state. The backend computes them once from the chain so each client doesn’t re-index Solana itself.

Under the hood

Merkle tree & nullifiers

Incremental Poseidon tree

Height 26 → ~67M leaves. Only the 26-level frontier is stored on-chain — not every leaf.

100-root history

A ring buffer keeps the last 100 roots. A withdraw must prove against a known root, which tolerates finality and reorgs.

The nullifier — one-way link

nullifier = Poseidon(commitment, index, sign) where sign = Poseidon(privkey,…). Spending reveals the nullifier; you can’t invert it back to the leaf or your key.

Double-spend guard

The program creates the nullifier account before moving any value — so a replay of the same proof can never succeed.

Running locally

How the pieces come up

  1. surfpool — a local Solana fork that also deploys the program.
  2. Postgres — the indexer’s database.
  3. cargo run -p privacy-cash-backend — brings up the backend (indexer + read-only API) on :8080.
  4. pcash — init a wallet, then deposit, scan, and withdraw.

Gotcha: the program ID in declare_id!, the deployed address, and the backend’s PROGRAM_ID env must all match (locally, whatever address you deploy to).

Deposit and withdraw run through the pcash client SDK. The protocol, backend, and SDK are real and wired together — no relayer in the submit path.
